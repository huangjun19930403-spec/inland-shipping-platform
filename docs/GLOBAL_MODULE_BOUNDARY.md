# 全局模块边界定稿

## 1. 系统管理

保留：

- 用户
- 角色
- 菜单
- 配置
- 字典
- 编码序列

定位：

- 管理员使用，不是普通业务主入口。
- 系统管理承载权限、菜单、配置、字典、编码序列等治理能力。
- 普通业务人员的日常入口应是数据标准化、货源数据、船舶数据、航线方案、数据分析、审核治理。

## 2. 字典管理

保留，但不是普通业务菜单重点。

说明：

- 业务人员不应频繁进入字典维护。
- 字典主要通过 seed 预制。
- 字典页面保留给管理员处理少量枚举治理、字典项启停、排序和排错。
- 后续菜单收敛时，字典管理可归入系统管理或管理员专用分组。

## 3. 标准货品模块

保留：

- 标准货品页面
- 标准货品详情
- 货品别名
- 包装形式
- 适配船型/节点/作业方式规则

删除/隐藏：

- 分类页面
- 类型页面

原因：

- 分类和类型是标准货品的筛选维度和 seed 数据，不是独立业务操作对象。
- 业务人员真正维护的是“标准货品及其别名、包装、适配规则”，不是频繁维护分类和类型。
- 后端现有 `commodity_category`、`commodity_type`、对应 API 和模型暂时保留，但产品定位降级为基础数据和筛选条件。

## 4. 地址与基础数据模块

保留：

- 行政区划
- 业务区域
- 运输节点
- 通航约束点

后续产品化目标：

- 地址与区域管理
- 运输节点地图化管理
- 节点能力档案
- 通航约束能力
- 标准化匹配日志

边界说明：

- 行政区划是基础底座，主要由 seed 初始化，不鼓励频繁人工编辑。
- 业务区域用于业务运营、分析统计和权限范围。
- 运输节点是装卸、换装、仓储、港区、码头等能力实体。
- 通航约束点是桥梁、船闸、浅滩、限航点等影响航线可行性的约束实体。
- 基础数据模块要服务货源标准化、船舶画像、航线方案和分析地图。

## 5. 船舶模块

保留：

- 船舶档案
- 船舶详情
- 船舶画像
- 船舶证书
- AIS/MMSI 信息

删除/隐藏：

- 船舶导入批次列表页
- 船舶导入批次详情页

导入方式：

- 放到船舶列表页作为“导入”动作。
- 返回导入结果摘要和错误明细下载。
- 不作为业务一级对象。

边界说明：

- 现有 `ship_import_batch`、`ship_import_raw`、`ship_import_record` 可先保留为导入过程日志。
- 后续第 7 轮重新评估是否降级为通用 `import_task` 或后台日志。
- 用户任务应围绕船舶档案、运力、证书、经营状态、MMSI/AIS、区域与流向画像展开。

## 6. 货源模块

保留并重构：

- 正式货源列表
- 手工录入
- 货源详情

新增方向：

- 采集批次
- AI解析池
- 候选确认池
- 质量看板

边界说明：

- `freight` 是正式货源，不应承担全部采集、原始消息、候选、确认、质量评分、重复判断职责。
- 后续第 6 轮可新增采集链路表，把“原始来源 -> AI解析 -> 候选 -> 人工确认 -> 正式货源”拆开。
- 正式货源需要服务分析模块，字段和状态必须足够支撑趋势、区域、流向、货品、渠道统计。

## 7. 航线模块

保留：

- 航线
- 路径方案
- 路径节点串
- 航段生成结果
- 地图展示

说明：

- 暂缓继续深做 4E。
- 后续第 8 轮统一重构。
- 现阶段保留 4B-4D 成果，不再新增局部编辑器能力。
- 旧航段主操作后续降级为节点串生成结果和调试信息。
- 航线最终产品链路必须是“节点串 -> 自动生成航段 -> geometry -> 约束影响 -> 可行性判断”。

## 8. 分析模块

必须重构为平台核心门面。

保留：

- 货源分析
- 船舶分析
- 分析任务

重构方向：

- 指标卡
- ECharts
- 地图
- 流向
- 热力
- 明细穿透

边界说明：

- 当前分析模块已有货源日汇总、城市、流向、货品、渠道、船舶城市、船舶流向、任务记录等统计表和分页 API。
- 后续第 4 轮要新增面向看板、图表和地图的聚合接口，不让前端硬拼分页表。
- 分析模块优先展示业务结果，再允许穿透到明细表。

## 9. 审核治理模块

保留：

- 审核任务
- 审核详情

后续扩展：

- 数据质量
- 标准化反馈
- 人工确认记录

边界说明：

- 审核治理不是单纯审批列表，而是数据进入正式业务库前后的质量控制中心。
- 后续应承接货源候选确认、标准化反馈、船舶档案质量、节点匹配争议、分析异常数据等治理事项。
- 数据质量页面可在第 6-7 轮后补齐，不在第 0 轮改页面。
